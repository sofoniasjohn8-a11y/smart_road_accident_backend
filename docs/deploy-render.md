# Deploying to Render (free tier)

The repository ships a [Render Blueprint](../render.yaml) that creates a free web service
plus a free PostgreSQL database and wires them together. Render builds this repository with
`npm ci` and runs `npm run db:migrate && npm start`.

> Free instances are for prototypes and demos. A free web service sleeps when idle and a free
> database is deleted about six weeks after it is created — see the limitations further down
> before pointing real hardware at it.

## 1. Create the services from the Blueprint

1. Push this repository to GitHub (or merge the pull request that contains `render.yaml`).
2. Sign up at [dashboard.render.com](https://dashboard.render.com) — no credit card is needed.
3. Choose **New > Blueprint**, connect the repository, and confirm the `render.yaml` it detects.
4. Render prompts for the two `sync: false` values in `render.yaml`:
   - **`DEVICE_API_KEYS`** — a JSON map of device ID to secret, each secret at least 32 characters:
     `{"ROAD_DEVICE_001":"<32+ character random secret>"}`.
     Generate one with `openssl rand -hex 24`. The same secret goes into the ESP32 firmware, and
     the API exits at boot if any secret is shorter than 32 characters.
   - **`CORS_ORIGINS`** — comma-separated browser origins, for example
     `https://my-dashboard.example.com`. Leave it empty when only devices, Postman and curl call
     the API; non-browser clients send no `Origin` header and are unaffected.
5. Apply. The first deploy creates the database, applies `src/db/schema.sql`, starts the API and
   waits for `GET /api/health` to answer.

`JWT_SECRET` is generated by Render. Never commit real secrets to the repository.

## 2. Verify the deployment

```bash
curl -s https://<your-service>.onrender.com/api/health
# {"status":"ok","database":"connected"}
```

An unauthenticated device report must still be rejected:

```bash
curl -s -X POST -H 'Content-Type: application/json' -d '{}' \
  https://<your-service>.onrender.com/api/accidents
# 401 {"error":"Valid device authentication headers are required."}
```

## 3. Create the first worker account

Free web services have no shell and cannot run one-off jobs, so create the account from your own
machine against the database's **external** connection string (Render dashboard > your database >
**Connect > External**):

```bash
npm ci
DATABASE_URL='<external connection string>' DATABASE_SSL=true \
  WORKER_EMAIL='you@example.com' WORKER_PASSWORD='a-private-12+-character-password' \
  npm run worker:create
```

Then log in against the deployed API to get a bearer token for `GET /api/accidents`
(see README.md, "API overview").

## 4. Point the ESP32 sketch at the service

```
API_URL = https://<your-service>.onrender.com/api/accidents
```

Sign each request as described in README.md ("Device signing and abuse prevention"): the device
secret must match the `DEVICE_API_KEYS` value configured above, the timestamp must be within
`DEVICE_SIGNATURE_TOLERANCE_SECONDS` (default 300 s), and each nonce may be used once.

## Free-tier limitations that affect this app

| Limit | Consequence here |
| --- | --- |
| Service **spins down after 15 minutes** idle; ~1 minute to wake | A device report sent to a sleeping instance can time out instead of being stored. Wake it with a `GET /api/health` first, or move to a paid always-on instance before relying on it. |
| Free PostgreSQL **expires 30 days** after creation (14-day grace, then deletion) | Incident data is temporary. Upgrade the database plan or export before expiry. |
| **No shell, no one-off jobs** | Migrations and `worker:create` cannot run in the dashboard container. Migrations run in the start command; create worker accounts from your machine (step 3). |
| **750 free instance hours** per workspace per month | An always-on service can exhaust this near the end of a long month; Render suspends free services until the month resets. |
| Single instance, ephemeral filesystem, no backups | Device replay state lives in process memory (see README limitations) and data lives only in PostgreSQL. |
| Workspace allows **one** free database | A second free database needs the first removed or upgraded. |

## Database SSL, and the one setting to check first

`render.yaml` uses the database's **internal** connection string (same region, private network)
with `DATABASE_SSL=false`. `src/db/pool.js` only supports *verified* TLS when `DATABASE_SSL=true`,
which requires the server certificate to match the host name.

If the service logs a TLS error at boot, change `DATABASE_SSL` in the Render dashboard
(**Environment**) and redeploy:

- `no pg_hba.conf entry ... no encryption` → the private network requires TLS. Set
  `DATABASE_SSL=true` **and** replace `DATABASE_URL` with the database's external connection
  string, whose certificate is publicly trusted. Keep the service and database in the same region
  if you can.
- `Hostname/IP does not match certificate's altnames` or `self-signed certificate in certificate
  chain` → the server certificate is not verifiable against Node's CA store. Use the external
  connection string with `DATABASE_SSL=true`; do not disable certificate verification.

## Going beyond the free tier

Move the web service to any paid instance type to remove the idle spin-down, and the database to a
paid plan to remove the 30-day expiry and enable backups. `render.yaml` needs no change beyond the
`plan` values, and the paid instance types also allow `preDeployCommand` if you prefer migrations
outside the start command.
